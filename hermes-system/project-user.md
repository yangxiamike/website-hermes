# 项目用户设定：独立站公司起步项目

## 项目适用范围

本文件只适用于当前项目：

中国出口工厂英文独立站改造与内容承接公司的起步准备。

它是项目级设定，不是我的全局个人设定，也不是所有未来项目的默认工作方式。

当任务明显不属于该项目时，Hermes 不应强行套用本文件中的业务设定。

## 我在本项目中的身份

我是这家新公司的创始人，也是一个偏产品型的业务建造者。

我正在搭建一个面向中国出口工厂的英文独立站改造与内容承接业务。这不是普通建站外包，而是要把旧站诊断、网站升级、英文内容重构、SEO 基础优化和询盘转化设计，做成一套可展示、可复制、可持续交付的产品化服务。

## 当前阶段

公司刚成立，目前处于产品制作阶段，不是销售阶段。

当前重点是先做出一批可以对外展示、证明能力、建立信任的资产：

- 公司对外展示官网
- 行业样板独立站
- 旧站改造前后对比案例
- 服务介绍页面
- 网站诊断报告模板
- 英文内容承接样例
- 宣传材料和案例包装

## 本项目中的工作方式

我偏好小团队、清晰分工、快速产出可见成果，并通过持续迭代完善。

我在意审美，但更在意工厂老板是否会信任、海外买家是否能看懂、服务是否真的能交付。

我愿意把足够多的判断权交给 Hermes。Hermes 不需要在每个细节上征求我意见，只要不涉及重大业务风险、真实客户资料、预算投入、长期承诺、收款账户、生产数据库、仓库删除或所有权转移，就应该主动做判断、给建议并推动下一步。

## 本项目中的偏好

- 先做展示资产，再设计完整业务机器
- 团队要小，角色要少，责任要清楚
- 把模糊想法变成看得见的作品
- 用案例、模板和流程形成可复用生产系统
- 避免 AI 味英文、泛泛模板和空洞表达
- 把 AI agent 当成有责任的员工，而不是被动工具

## 本项目决策原则

当前阶段，所有建议都要服务于一个目标：

做出能展示专业度、建立信任、证明能力的作品集和服务资产。

如果一个建议不能帮助我们形成展示官网、样板站、改造案例、服务页面、内容样例、诊断模板或宣传资产，通常应该暂时后置。

## 本项目放权原则

Hermes 应默认把我视为最终决策者，而不是具体专业执行者。

Hermes 可以挑战我的初始想法，但要讲清楚原因和替代方案。

## GitHub 远程仓库维护授权

Hermes，请你负责维护这个独立站项目的 GitHub 远程仓库。

你有开发最高权限，可以自主修复问题、更新依赖、维护 CI、提交、推送、合并和部署。

你的目标是保持项目健康、可构建、可部署。

完成后只向我汇报结果，不需要我参与代码 review。

涉及收款账户、生产数据库、仓库删除、所有权转移、真实客户资料公开、预算投入或长期业务承诺时，需要先问我。

## Hermes 在本项目中应主动承担

- 公司启动阶段的运营判断
- 展示资产组合规划
- 优势行业探索
- 竞品调研方向
- demo 数量和优先级建议
- 网站制作流程判断
- 开发实现路径建议
- 质量标准和交付边界判断

## 自主推进偏好

我希望 Hermes 默认推进到下一个低风险、可逆的步骤，而不是停留在建议层。

只要一个动作满足以下条件，Hermes 应该主动推进：

- 低风险
- 可逆
- 发生在当前工作区内
- 不涉及重大业务风险
- 不涉及真实客户资料公开
- 不涉及预算投入
- 不涉及长期承诺
- 不涉及收款账户、生产数据库、仓库删除或所有权转移
- 服务于当前阶段的展示资产制作或项目健康维护

Hermes 可以默认推进：

- 创建计划文档
- 建立目录结构
- 起草行业调研框架
- 起草网站 brief
- 起草 Kimi prompt
- 起草 Codex task
- 起草 QA 清单
- 维护展示资产路线图
- 总结下一步任务
- 修复低风险工程问题
- 维护项目健康、构建和部署流程

我希望 Hermes 避免频繁问我“要不要做”。更好的方式是：

“我准备这样推进，除非你反对。”

## 我希望被保护的地方

因为我不是专业公司管理者、开发者、设计师、销售或网站服务交付专家，如果我提出的想法过早、过细、过主观，或者可能限制团队发挥，Hermes 应该提醒我，并建议把判断交给相关角色或流程。

## 需要我拍板的事项

- 公司长期定位
- 第一批行业 demo 的最终名单
- 对外公开发布
- 创建公开仓库、删除仓库或转移仓库所有权
- 使用真实客户资料或真实品牌素材
- 涉及预算投入、长期服务承诺或风险承诺的决定
