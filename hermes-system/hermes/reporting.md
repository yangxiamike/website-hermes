# 汇报规则

## 汇报渠道

飞书是 Hermes 向创始人同步进展、风险和决策点的外部汇报渠道。

飞书不是内部流水账，也不是所有过程都要同步的地方。

## 汇报原则

Hermes 不需要汇报所有过程，只汇报结果、风险和需要创始人拍板的问题。

默认原则：

- 少噪音
- 重结果
- 重风险
- 重下一步动作
- 重需要创始人拍板的事项

## 必须汇报的情况

Hermes 必须通过飞书汇报：

- 完成一个阶段性任务
- Mira 完成关键网站 brief 或内容方案
- Dex 完成原型或工程版本
- Nora 完成 QA Gate
- 出现 P0 问题
- 出现阻塞或重大风险
- 需要创始人拍板
- 资产准备进入对外展示库
- 涉及公开展示、真实客户资料、预算投入、长期承诺、收款账户、生产数据库、仓库删除或所有权转移

## 不需要默认汇报的情况

以下事项不需要默认通过飞书汇报：

- 每个小想法
- 每次普通文件修改
- 内部角色讨论过程
- 低风险、可逆的小步骤
- 普通格式调整
- 无风险的工程小修复

这些内容可以在阶段性汇报中总结，不需要实时打扰创始人。

## 默认汇报格式

```text
Hermes 工作汇报

当前状态：

完成事项：

发现问题：

下一步默认推进：

需要创始人拍板：

风险提醒：
```

## QA 汇报格式

当 Nora 完成 QA Gate 时，Hermes 应使用：

```text
Hermes QA 汇报

资产名称：
QA 结果：Pass / Conditional Pass / Fail

P0 问题：

P1 问题：

P2 问题：

下一步处理：

是否需要创始人拍板：
```

## 拍板请求格式

当需要创始人决策时，Hermes 应使用：

```text
Hermes 拍板请求

需要决策：

背景：

推荐选项：

备选方案：

风险：

如果 24 小时内没有回复，我建议：
```

## 升级原则

第一阶段只使用飞书做轻量汇报网关。

不要一开始把飞书变成复杂自动化运营中枢。等展示资产制作流程稳定后，再考虑：

- 自动日报
- 项目看板
- 关键节点审批
- 资产状态同步
- GitHub / 部署状态通知
